# نظام إدارة ضباط المخاطر

> تطبيق ويب عربي (RTL) متكامل لإدارة قسم المخاطر في شركة تمويل أصغر: ملفات ضباط المخاطر، دقائق الصرف اليومية، الزيارات الميدانية ودورات مراجعة التقارير، سجل الملاحظات، التقييمات الشهرية والسنوية، لوحة معلومات تفاعلية، وتقارير موظفين قابلة للطباعة/التصدير PDF.

**كل البيانات تُخزَّن محليًا في متصفح كل مستخدم (IndexedDB). لا يوجد خادم، ولا مزامنة، ولا إرسال بيانات، ولا تتبّع.**

- لا يحتاج المستخدم إلى Node.js، أو خادم محلي، أو تثبيت أي شيء: الموقع بعد النشر يعمل مباشرة في المتصفح.
- يعمل دون اتصال بعد الزيارة الأولى (عبر Cache API و عامل خدمة يخزّنان **أصول التطبيق فقط**).
- يعمل تحت أي مسار فرعي لمستودع GitHub Pages (`https://username.github.io/repo-name/`).

### سلوكيات مهمة

- **البيانات التجريبية معزولة تمامًا**: كل سجل تجريبي يحمل `isDemo=true` ولا يظهر مع السجلات الفعلية، ولا يُصدَّر في CSV، ولا يدخل حسابات لوحة المعلومات إلا عند تفعيل «وضع البيانات التجريبية». ويمكن حذفها كلها في أي وقت دون أي أثر على البيانات الفعلية.
- **الحذف الناعم**: لا يُحذف أي سجل فعليًا عند الأرشفة؛ تُملأ `deletedAt` ويظهر السجل في تبويب «المؤرشفون/المؤرشفة» مع إمكانية الاستعادة.
- **سجل التغييرات**: كل إنشاء/تعديل/أرشفة/استعادة/اعتماد/فتح يُسجَّل محليًا (أحدث 500 إدخال في الشاشة).
- **منع اليتامى**: لا يمكن أرشفة فرع مرتبط بموظفين، ولا الحذف النهائي لموظف له سجلات مرتبطة.

## <a id="الخصوصية"></a>2) الخصوصية والتخزين المحلي

- **IndexedDB** هي قاعدة البيانات الأساسية (اسمها `risk-officer-management`، بإصدار مخطط وترقيات مُدارة).
- **localStorage / meta** تُستخدم فقط لتفضيلات خفيفة (مثل وضع البيانات التجريبية، ومؤشرات التشغيل).
- **Cache API + Service Worker** لتخزين **أصول التطبيق** (HTML/JS/CSS/الخطوط) للعمل دون اتصال — ولا تُخزَّن أي سجلات عمل هناك أبدًا.
- لا توجد أي طلبات شبكة إلى خادم أو API خارجي، ولا تحليلات، ولا خطوط أو مكتبات من CDN. الخطوط العربية (Cairo) والأيقونات والرسوم كلها مضمّنة داخل الحزمة.

### تحذيرات يجب عرضها على المستخدمين

> **مساحة المتصفح ليست نسخة احتياطية دائمة.** قد تُفقد البيانات إذا: حذف المستخدم «بيانات التصفح»، أو استخدم وضع التصفح الخاص/المتخفي، أو أعاد تثبيت المتصفح أو النظام، أو امتلأت مساحة التخزين، أو غيّر إعدادات الحماية. **البيانات غير مشفّرة افتراضيًا**، وأي شخص يستطيع استخدام الجهاز/المستخدم نفسه قد يصل إليها (استخدم تشفير القرص/حساب مستخدم مؤمَّن على مستوى نظام التشغيل).
>
> لذلك: **صدّر نسخة JSON دوريًا** واحفظها في مكان آمن. النسخة الاحتياطية تحتوي بيانات كاملة غير مشفرة، لذا يجب حمايتها.

**ما يُنشر على GitHub:** الكود المصدري فقط. لا تُرفع أي ملفات نسخ احتياطية أو بيانات عمل (ملف `.gitignore` يمنع `*backup*.json` و`data/` و`exports/` وغيرها). تُضاف البيانات من كل مستخدم داخل متصفحه الخاص على جهازه، ولا تظهر لأي شخص آخر.

## <a id="التشغيل"></a>3) التشغيل المحلي (للمطوّرين فقط)

> لا يحتاج **مستخدم** التطبيق إلى أي من هذه الخطوات؛ هذه الخطوات لمن يريد تعديل الكود أو إعادة البناء.

```bash
npm ci          # تثبيت التبعيات من ملف القفل
npm run dev     # خادم تطوير على http://localhost:5173
npm test        # تشغيل الاختبارات (Vitest)
npm run build   # فحص الأنواع + بناء الإنتاج في dist/
npm run preview # معاينة نسخة الإنتاج
```

المتطلبات: Node.js 20+ (تم البناء والاختبار على Node 20.20.2). **وقت التشغيل في المتصفح لا يحتاج Node إطلاقًا.**

## <a id="النشر"></a>4) النشر على GitHub Pages

### الطريقة الأولى: GitHub Actions (موصى بها — مُعدَّة مسبقًا)

1. أنشئ مستودعًا جديدًا على GitHub وارفع الملفات:
   ```bash
   git init
   git add .
   git commit -m "نظام إدارة ضباط المخاطر"
   git branch -M main
   git remote add origin https://github.com/<USERNAME>/<REPO>.git
   git push -u origin main
   ```
2. من المستودع: **Settings → Pages → Build and deployment → Source: GitHub Actions**.
3. ملف `.github/workflows/deploy.yml` سيقوم تلقائيًا بـ: `npm ci` ← فحص الأنواع ← الاختبارات ← البناء ← النشر.
4. الرابط: `https://<USERNAME>.github.io/<REPO>/`.

### الطريقة الثانية: بناء محلي ثم رفع مجلد `dist`

```bash
npm ci && npm run build
npx gh-pages -d dist -b gh-pages      # أو ارفع محتوى dist يدويًا إلى فرع gh-pages
```
ثم Settings → Pages → Source: **Deploy from a branch** → الفرع `gh-pages` / المجلد `/ (root)`.

### المسارات الفرعية

- إعداد `base: './'` في `vite.config.ts` يجعل جميع المسارات نسبية، فتعمل الصفحة على النطاق الجذري وعلى أي مسار فرعي دون تعديل.
- التوجيه داخل التطبيق يعتمد على الـ **hash** (`#/employees`) فلا تظهر أخطاء 404 عند التحديث أو عند فتح رابط مباشر، ولا حاجة لقواعد إعادة توجيه.
- ملف `public/.nojekyll` و`public/404.html` يُنسخان تلقائيًا إلى `dist`.
- **اسم المستودع واسم المستخدم لا يظهران في الكود**؛ لا حاجة لأي تعديل قبل النشر.

> ملاحظة: النشر على GitHub Pages يتطلب مستودعًا **عامًا** (أو خطة تسمح بـ Pages الخاص). الكود عام، أما بيانات العمل فلا تخرج من متصفح كل مستخدم.

## <a id="النسخ-الاحتياطي"></a>5) النسخ الاحتياطي والاستعادة

من **الإعدادات → النسخ الاحتياطي**:

- **تصدير نسخة كاملة (JSON)**: يحتوي الإعدادات + كل الكيانات (فروع، موظفون، دقائق، زيارات، ملاحظات، تقييمات)، مع `formatVersion` و`schemaVersion` وعدد السجلات و**بصمة SHA-256** للبيانات.
- **التحقق قبل الاستعادة**: يتحقق النظام من هوية الملف، الإصدار، وجود كل الأقسام، سلامة كل سجل، عدم تكرار المعرّفات، ومطابقة البصمة؛ ويعرض تحذيرات للعلاقات المفقودة. لا يبدأ الاستعادة إن كانت النسخة غير صالحة.
- **نسخة أمان قبل الاستبدال**: قبل أي استبدال تُنشأ نسخة أمان من بياناتك الحالية فورًا (مع إمكانية تنزيلها).
- **وضعان للاستعادة**:
  - `استبدال`: يمسح السجلات الحالية ويضع محتوى النسخة.
  - `دمج`: يضيف/يحدّث بالسجلات، وعند تعارض المعرّف يُعتمد الأحدث `updatedAt`.
- **حذف كل البيانات**: يتطلب تأكيدًا صريحًا، وينشئ نسخة أمان أولًا.

**توصية تشغيلية**: تصدير نسخة أسبوعيًا (أو يوميًا) مع تسمية واضحة، والاحتفاظ بعدة نسخ، وعدم إرسال الملف عبر قنوات غير آمنة.

## <a id="csv"></a>6) الاستيراد والتصدير CSV

- التصدير من **الإعدادات → الاستيراد والتصدير** لأي كيان، أو من أزرار التصدير داخل الشاشات (النتائج المفلترة).
- الترويسات عربية مقروءة (`الرقم الوظيفي`, `الاسم`, `الفرع`, `الحالة`, …) والمقياس مكتوب كنص عربي (`على رأس العمل`, `متوسطة`, ...) لتسهيل التحرير في Excel.
- ملف التصدير يبدأ بـ BOM (`\ufeff`) لعرض العربية بشكل صحيح في Excel.
- الاستيراد يعرض **معاينة**: عدد الصفوف الصالحة، الأخطاء (صف برقم وسبب)، والتحذيرات. لا يُحفظ أي صف غير صالح.
- يتحقق الاستيراد من: الأعمدة المطلوبة، وجود الموظف/الفرع المرتبط بالاسم، صحة التواريخ والأرقام.
- السجلات التجريبية تُستبعد من التصدير افتراضيًا.

## <a id="الحساب"></a>7) قواعد الحساب (بدون اختراع سياسات)

### زمن العمل والمهل (دقائق الصرف)

- تُحسب المدد **داخل ساعات العمل وأيام العمل فقط**، وتُستثنى العطلات الرسمية المسجلة في الإعدادات.
- **المهلة الافتراضية 60 دقيقة عمل** (قابلة للتغيير)، وتُبنى على `وقت الاستلام` + المهلة = **الموعد النهائي**.
- **زمن معالجة الضابط** = مجموع الفترات التي لم يكن فيها طلب معلّق على الفرع/المعلومات.
- **زمن انتظار الفرع/المعلومات** = مجموع الفترات من `طلب الملف` حتى استلامه، ومن `طلب الاستيضاح` حتى الرد عليه (والطلبات الأخرى من نفس النوع).
- حالة الالتزام: `داخل المهلة` / `تجاوز المهلة` (للمغلقة)، و`جارٍ داخل المهلة` / `قارب المهلة` (عند بلوغ نسبة التنبيه) / `متأخر` (للمفتوحة التي تجاوزت الموعد).
- الطوابع الزمنية تُتحقق من الترتيب الزمني (لا يُقبل رد نهائي قبل الاستلام… إلخ).

### التقييمات

- **لا توجد أوزان ولا معادلات ولا عتبات تصنيف رسمية** — لم تُخترع أي منها.
- **المتوسط الافتراضي = مجموع الدرجات المسجلة ÷ عدد المعايير المسجلة**. المعايير غير المسجلة لا تدخل المقام، وتُعرض صراحةً كـ«معايير ناقصة».
- المقياس قابل للتخصيص (افتراضيًا 1–5)، والمتوسط يعرض البسط والمقام دائمًا ليكون الحساب شفافًا.
- التقييم السنوي يمكن **اشتقاقه** من التقييمات الشهرية: لكل معيار يُحسب متوسط الدرجات المسجلة في شهور تلك السنة (مع إظهار عدد الشهور المستخدمة).
- التقييم **المعتمد محفوظ من التعديل**؛ ويمكن فتحه للتعديل **بسبب موثق** يُحفظ في السجل.
- `thresholds` في الإعدادات (نسبة التزام مستهدفة، حد تأخر التقرير، نافذة التكرار، …) تُستخدم **للتنبيه والمقارنة فقط**، وليست معادلات رسمية. القيم الافتراضية محايدة (0 = بلا هدف).

- تشغيل النسخة المبنية (`vite preview`) وتصفح كل الشاشات **بدون أي خطأ في وحدة التحكم** (`CONSOLE ERRORS: []`).
- تفعيل البيانات التجريبية من الواجهة، ثم تصفح: لوحة المعلومات، الموظفون، ملف موظف، الدقائق، الزيارات (ونافذة تفاصيل بدورات المراجعة)، الملاحظات، التقييمات (ونموذج التقييم)، التقرير، والإعدادات — مع لقطات شاشة للتحقق البصري.
- **التحقق من العمل دون اتصال** (نسخة الإنتاج): تسجيل عامل الخدمة ناجح (`active`) وخُزِّن **30 أصلًا** في `roms-assets-*`، ثم قُطع الاتصال وأُعيد تحميل الصفحة →
  نجح التحميل من الذاكرة المؤقتة (`FAILS AFTER OFFLINE: []`, `offline reload ok: true`).
  > أثناء هذا التحقق اكتُشف خطأ حقيقي في مطابقة الأصول المخزنة (تعارض مع ترويسة `Vary` التي يضيفها خادم المعاينة) وأُصلح باستخدام `cache.match(..., { ignoreVary: true })`.
- **التحقق من مسار فرعي شبيه بـ GitHub Pages**: نُشر البناء في `/demo-repo/` على خادم محلي →
  التطبيق يعمل، لوحة المعلومات تُظهر 8 بطاقات، التقرير يُولّد صفحتين، ونطاق عامل الخدمة `http://…/demo-repo/` والأصول المخزنة داخل `/demo-repo/assets/...` (`errors: []`).
- **طباعة التقرير إلى PDF فعليًا**: تقرير من صفحتين A4 مع تحقق برمجي من عدم تجاوز المحتوى للارتفاع المتاح في كل صفحة (`bodyScroll ≤ bodyClient`)، وأن ملف PDF الناتج يحتوي **صفحتين** فعلًا.
- **`npm ci` من ملف القفل** يعمل من الصفر ثم الاختبارات والبناء (نفس خطوات GitHub Actions).

## <a id="اسئلة"></a>10) أسئلة شائعة ومشاكل معروفة

**لا أرى بياناتي بعد تحديث الصفحة؟**
تأكد أنك تستخدم المتصفح والجهاز والملف الشخصي نفسه، وأنك لست في وضع التصفح الخاص. البيانات محلية ولا تُزامَن بين الأجهزة.

**هل يمكن لعدة موظفين العمل على نفس البيانات؟**
لا. لا يوجد خادم ولا مزامنة بالتصميم (خصوصية كاملة). كل مستخدم لديه قاعدته المحلية؛ ويمكن تبادل البيانات عبر ملف نسخة احتياطية (مع مراعاة أنها غير مشفرة).

**هل البيانات مشفّرة؟**
لا، غير مشفّرة افتراضيًا في IndexedDB. استخدم حساب نظام مؤمَّنًا وتشفير القرص عند الحاجة.

**لا يعمل التطبيق دون اتصال؟**
العمل دون اتصال يُفعَّل بعد أول زيارة ناجحة للنسخة المنشورة (يسجّل عامل الخدمة أصول التطبيق). في بيئة التطوير `npm run dev` لا يُسجَّل العامل.

**الطباعة تُخرج صفحة فارغة أو صفحات إضافية؟**
استخدم زر «طباعة / حفظ PDF» داخل شاشة التقارير (يُفعّل نمط الطباعة تلقائيًا). تأكد من إلغاء تفعيل رؤوس/تذييلات المتصفح (Headers and footers) وخيار «Scale: Default 100%» للحصول على صفحات A4 مطابقة للمعاينة.

**الخطوط تبدو مختلفة؟**
الخطوط (Cairo) مضمّنة محليًا في الحزمة؛ إن حجب المتصفح الخطوط المحلية فسيرجع إلى خط النظام العربي.

**هل يمكن استعادة نسخة من إصدار أقدم من التطبيق؟**
نعم إذا كان `formatVersion` مدعومًا. النسخ من إصدار أحدث تُرفض برسالة واضحة (حدّث التطبيق أولًا). ترقيات المخطط تُنفَّذ تلقائيًا عند أول فتح بعد التحديث.
